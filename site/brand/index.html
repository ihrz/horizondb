Usage rules

Give it room, keep it dusk

The mark is a sunset seen from one fixed point. Leave it as drawn and it reads at any size.

¼ w ¼ w

Clear space

Keep at least a quarter of the mark's width free on every side: no text, edge or other logo inside it.

Minimum sizes

Mark: 16 px, where the rows still separate. Wordmark: 24 px tall, so "DB" keeps its gradient readable. Below that, use the mark alone.

Don't recolour it outside the palette.

Short

HorizonDB is the key-value server behind iHorizon. Written in Rust, it answers every read and write from memory over a single WebSocket, then flushes your JSON documents to PostgreSQL in batches. Dot keys address inside documents, mutations return their result, and a zero-dependency TypeScript client for Bun speaks the protocol.

Long

HorizonDB is a JSON key-value server written in Rust (edition 2024), built for the iHorizon Discord bot. A bot hammers a handful of large JSON documents from many shards at once: a SQL round trip on every write is too slow, and memory alone forgets on restart. HorizonDB sits on the line between the two. Every get, set, add and push is served from memory, behind a lock per document, and edits in place. Every few minutes a background task flushes the changed keys to plain PostgreSQL tables with batched UNNEST upserts; a graceful shutdown flushes everything first. Idle documents are packed about ten times smaller, and clean ones leave memory until they are needed again. Clients speak JSON over one WebSocket, with pipelined requests and answers that carry their result. A zero-dependency TypeScript client for Bun ships in the repository. The wire protocol may still change.

LinkedIn / Reddit
HorizonDB: a JSON key-value server that keeps memory above and PostgreSQL below

A Discord bot hammers a few large JSON documents (a guild, a member, a counter) from many shards at once. A SQL round trip on every write makes that slow; a pure in-memory store forgets everything on restart. HorizonDB, the server behind the iHorizon bot, sits on the line between the two.

How it works:
- Every read and write is served from memory. A push into a multi-megabyte document edits it in place instead of copying it.
- Every flush_interval_secs (300 s by default), changed keys go down to plain PostgreSQL tables in batched UNNEST upserts. A graceful shutdown flushes everything first; a crash can lose up to one interval of writes, and you choose that interval.
- Read-modify-write is serialized per key: sixteen workers on one counter end on the exact sum, checked on every benchmark run.
- Idle documents are packed about ten times smaller in memory. In one measurement (release build, 200 000 documents of about 1 KB), resident memory after 80 s idle went from 2 703 MiB to 60 MiB with idle eviction, or 360 MiB with every document kept in memory.

It is written in Rust (2024 edition, unsafe forbidden), speaks JSON over a single WebSocket, and ships a zero-dependency TypeScript client for Bun. Still a work in progress: the wire protocol may change.

Un bot Discord martèle quelques gros documents JSON (une guilde, un membre, un compteur) depuis de nombreux shards en même temps.
